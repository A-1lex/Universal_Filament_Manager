# Постійні правила роботи над UFM Studio

Відповідати користувачу українською.

## Доступні ліміти та автоматичне продовження

Користувач дозволив автоматично продовжувати узгоджений план без повторних
погоджень. Системні дозволи й обов’язкові схвалення залишаються чинними.
Перед роботою, між етапами та перед витратними операціями перевіряти основні
ліміти Codex. Якщо залишок п’ятигодинного або тижневого вікна становить
15% чи менше, зберегти прогрес і завершити запуск до відновлення лімітів.
Якщо дані лімітів недоступні, не починати тривалий етап. Відсоток залишку:
100 мінус usedPercent. Баланс додаткових платних кредитів не є відсотком
основних лімітів. Не купувати кредити й не використовувати скидання лімітів.
Активна погодинна автоматизація `ufm` перевіряє можливість продовження;
порогова зупинка не означає вимкнення самої автоматизації.

Після кожного завершеного етапу обов’язково перевіряти ліміти. Якщо обидва
залишки понад 15% та є доступний незавершений крок, одразу продовжувати
його у цьому самому запуску, без повторного погодження та очікування
погодинної автоматизації. Не завершувати запуск лише через завершення
одного етапу або готовність звіту. Зберігати проміжні checkpoints і рухатися
далі до порога лімітів, завершення плану, реального блокування чи системного
переривання. Це уточнення користувача від 2026-10-27.

## План і збереження прогресу

На початку кожної робочої сесії читати:
1. `docs/PROJECT_PROGRESS_UK.md` — актуальний стан і найближча дія.
2. `docs/INTEGRATION_CHECKLIST_UK.csv` — статуси 118 кроків.
3. `docs/INTEGRATION_STEP_BY_STEP_UK.md` — повний план із критеріями приймання.
4. Потрібні останні записи `docs/DEVELOPMENT_HANDOFF.md` — технічні подробиці.

Після кожного змістовного етапу та перед завершенням відповіді:
- Оновити відповідні рядки CSV, зберігаючи ID й формат UTF-8 BOM.
- Використовувати статуси: `Заплановано`, `У роботі`, `Частково виконано`,
  `Виконано`, `Заблоковано`, `Відкладено`.
- Позначати `Виконано` лише після перевірки всіх вимог конкретного кроку;
  записувати доказ: файл, тест, артефакт або перевірений результат.
- Для часткового виконання записати зроблене й те, що залишилося.
- Оновити PROJECT_PROGRESS_UK.md: дата, виконане, незавершене, перевірки,
  обмеження, наступна конкретна дія та підрахунок статусів CSV.
- Після змін коду або збірки додати технічну точку продовження в
  DEVELOPMENT_HANDOFF.md. Не стирати попередні докази й застереження.
- Робити проміжні точки збереження під час довгої роботи, не чекати
  вичерпання контексту. Точний залишок контексту може бути недоступний.

Наявна реалізація не означає завершення нового кроку плану без перевірки.
Відсоток закритих кроків — це частка повністю виконаних пунктів, а не
відсоток готовності продукту; не видавати приблизну оцінку за вимірювання.
Розрізняти зміни вихідного коду, перевірену збірку й установлену програму.
Якщо завдання перервано, залишити точну незавершену дію та спосіб перевірки.

Реальні бази, секрети, резервні копії, `linked-stack` і власні зміни
HaspelSync берегти. Не змінювати облік залишків прямими SQL-записами.

## Додаткові перевірені джерела

- Для питань про архітектуру, потоки даних, зв’язки модулів чи місце
  реалізації спершу використовувати наявні карти з
  `D:/graphify-out/bambu-ufm/PROJECT_MAPS_UK.md`: карту UFM для внутрішніх
  модулів, Spoolman для його API/схеми/клієнтів, карту зв’язку Spoolman↔UFM
  для меж інтеграції та зведену карту для наскрізних шляхів. Для фактів про
  Bambu читати `HANDOFF_UK.md` і `ENRICHMENT_UK.md`. Граф — засіб пошуку й
  навігації: перед зміною або висновком перевіряти живий код і відповідні
  тести/fixtures; ребро графа саме по собі не доводить runtime-поведінку.
- Перед аналізом Bambu Studio для logical filament, `print.mapping`, AMS-slot,
  RFID spool та refill-подій читати
  `D:/graphify-out/bambu-ufm/HANDOFF_UK.md` та, для доказових зв’язків,
  `D:/graphify-out/bambu-ufm/ENRICHMENT_UK.md`. Основна спільна карта:
  `D:/graphify-out/bambu-ufm/enriched/graphify-out/graph.json`. У звітах описані графи локальних
  профілів і вихідного коду, точні шляхи першоджерел, межі parser coverage,
  provenance та відтворювані команди. Цей граф є навігаційним засобом; кожну
  поведінку підтверджувати вихідним кодом/fixture або тестом, а буквальну
  згадку поля не вважати доказом потоку даних чи підтримки запису прошивкою.
