# Паритет функцій і готовність настільного UFM до розповсюдження

Дата оцінки: 25 жовтня 2026 року.

Оновлення 26 жовтня: додано Qt Studio, автономну попередню EXE-збірку та
обмежене атомарне ядро однокотушкової фіналізації. Детальний актуальний стан —
[FEATURE_MATRIX_UK.csv](FEATURE_MATRIX_UK.csv) та
[AUTOMATIC_ACCOUNTING_UK.md](AUTOMATIC_ACCOUNTING_UK.md).
Нижче збережено базу порівняння; повний паритет і release gates залишаються відкритими.

## 1. Поточний висновок

Наявний UFM ще не має всього функціоналу Spoolman і HaspelSync та не є готовим автономним продуктом для широкого розповсюдження. Є ядро, сховище, рання desktop-оболонка та окремі інтеграції. Затвердження архітектури, встановлення `uv`, збірка Python wheel або поява `.exe` не підтверджують готовність усіх сценаріїв.

Основні незавершені частини: повне наповнення Qt UI, багатоматеріальна фіналізація,
стійкий фоновий цикл, робота з файлами друку/AMS, узгоджений перехід даних і
перевірений на чистій Windows дистрибутив. PySide6 доданий як optional desktop dependency.

Ціль: одна розширювана програма без браузера, Docker та обов’язково запущених Spoolman/HaspelSync.

## 2. Що означає «ті самі функції»

База порівняння: локальні вихідні коди Spoolman 0.27.0, HaspelSync 1.3.4 та локальні доповнення checkout `1.3.4-local.1`. Майбутні версії сторонніх проєктів не змінюють цю базу автоматично.

Паритет перевіряється сценарієм: користувач виконує дію, отримує коректний результат, дані зберігаються, повторення та відновлення працюють. Екрани відтворюються нативними віджетами. Наявність класу, таблиці або кнопки без завершеного сценарію не є готовою функцією.

Стани рядка матриці: **основа → реалізовано → автоматично перевірено → прийнято в зібраній програмі**. Окремо записується доказ перевірки обладнання. Опис нижче є оглядом коду, а не результатом нового повного запуску тестів.

## 4. Відмінності, які потрібно назвати явно

Нативний інтерфейс замінює вебклієнт, а desktop-інсталятор замінює контейнерну інсталяцію. Журнал UFM зберігає історію й виправлення, тому видалення використаної котушки потребує погодженого правила замість стирання обліку.

- **Сторонні програми.** Підтримка принтера Moonraker або OctoPrint не означає сумісність зі Spoolman API. Home Assistant, API/WebSocket, сторонні клієнти та Prometheus потребують власних контрактів. Це може бути опційний інтерфейс усередині настільного продукту; браузер або окремий Spoolman для UI не потрібні.
- **Серверні БД.** Ціль використовує SQLite. Підтримку PostgreSQL/MySQL/CockroachDB старого Spoolman не можна оголосити перенесеною без окремих реалізації та перевірки.
- **Телефон/мережевий доступ.** Віддалений клієнт та його автентифікація є окремою функцією, яку нативне вікно саме по собі не забезпечує.
- **Обладнання.** Список моделей Bambu, AMS і прошивок складається за фактичними перевірками. Початковий сценарій P1S не доводить підтримку всього переліку README HaspelSync.
- **Мови.** uk/en є поточною базою UFM; повний набір перекладів Spoolman не підтверджений.

Ці пункти не вилучаються з порівняння мовчки. Для кожного в scope випуску записується: підтримано, заплановано або свідомо змінено з поясненням.

## 5. Порядок до робочої програми

1. **Зафіксувати матрицю F01–F21:** очікувані результати, sanitized fixtures і журнал доказів.
2. **Завершити облікове ядро:** передумови й фазу 6, одну фіналізацію, атомарність, сегменти, резерви та відновлення. Таблиці фіналізації не замінюють прикладну команду.
3. **Реалізувати PySide6 desktop:** інвентар, історію й інші потрібні сторінки через прикладні порти, uk/en та offline-роботу.
4. **Завершити цикл принтера:** workers, MQTT/TLS, FTPS, 3MF/G-code, ідентичність запуску, призначення і фіналізацію. Автоматичні події підключати до перевіреного ядра.
5. **Закрити функціональні прогалини:** каталог, поля/групування, AMS, етикетки, зважування, вартість, звіти й визначену сумісність.
6. **Провести перехід на копії даних:** ID, залишки, локації, мітки, історію та невизначені записи. Історичний дебет, уже врахований у початковому залишку, не списується повторно.
7. **Зібрати кандидата й перевірити саме його:** чисте Windows-середовище, користувацькі сценарії, обладнання та відновлення.
8. **Оформити розповсюдження:** інсталятор, версію, залежності, оновлення, документацію, notices та результати перевірок.

Меншу тестову версію з однією вертикаллю можна позначити як обмежену alpha/beta. Вона не підтверджує повного паритету двох вихідних програм.

Неправильний залишок, повторне списання, втрата даних, непридатне відновлення, витік секретів або неможливість запуску заявленого артефакту блокують випуск. Готовність інших екранів цього не компенсує.

Доказ містить дату, ОС, версію/хеш збірки, конфігурацію пристрою, результат і межі перевірки. Старий запуск тестів із checkout не підтверджує новий інсталятор.

## 7. Збірка та пакет

Офіційний `pyside6-deploy` використовує Nuitka та створює виконуваний пакет із залежностями. Це кандидат для build-процесу після появи нативної точки входу. Конкретні версії й режим пакування потрібно зафіксувати в конфігурації, без покладання на змінні типові значення.

Виконуваний пакет та інсталятор є різними результатами. Інсталятор додає погоджені каталоги, ярлики й процедуру видалення/оновлення. Deployment tool не замінює перевірку даних, UI, пристрою й ресурсів UFM.

`uv` потрібен для відтворюваного середовища розробки/збірки. Користувач готової програми не повинен встановлювати його для запуску.

Джерело щодо інструмента: [офіційна документація pyside6-deploy](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html). Цей документ не встановлює Qt/Nuitka та не створює дистрибутив.

## Feature parity audit: monitor і durable receipts — 2026-10-30

Перевірив джерела графом і звірив live source. `PrinterMonitorTask` (QThread) має exponential retry 1–30 s, періодичну 15-second health перевірку та Windows sleep/resume detector. Studio запускає його вручну для вибраного принтера й зупиняє при вимкненні моніторингу або закритті. Bambu LAN provider отримує MQTT reports і генерує зміни job observations. Але UI `show_latest_monitored_event()` викликає `take_latest_event()`, який вичищає буфер і повертає лише останню подію; `show_monitored_event()` тільки змінює текст панелі. Автоматичної подачі provider event до durable receipt ingestion не виявлено.

`ReceiptIngestion.ingest()` перевіряє обмежений protocol payload і printer scope, створює durable `PENDING` receipt у UFM UnitOfWork, повертає наявний receipt при тотожному повторі та створює reconciliation conflict при зміненому payload. Це application primitive, але воно не wired до `PrinterMonitorTask` і саме не проектує/фіналізує accounting. Feature matrix F048 та F071 виправлено з `Додати` на `Частково`; їхні докази й межі записано в `FEATURE_PARITY_MAPPING_UK.csv`. Matrix: 124; Є 28 / Частково 30 / Додати 46 / Бажано 20. Integration checklist лишається 118 рядків із незміненими статусами. Source review only: тести, UI, принтер, runtime не запускалися.

Наступна реалізація має персистувати provider events до UI coalescing; окремий consumer має відновлювати pending receipts після restart з idempotency/reconciliation, не списувати з callback. Спершу потрібні bounded durable inbox, backpressure і lifecycle у Studio; E03.07 legacy AMS PATCH writer fence лишається блокером автосписання.
