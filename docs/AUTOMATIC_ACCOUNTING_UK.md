# Автоматичне списування: стан і план реалізації

## Висновок аудиту

Додано обмежене атомарне ядро `src/ufm/application/finalization.py`:
`FinalizationCommands.finalize_single`. Воно використовує вже збережені факти
одного завершеного друку на одній котушці. Пройшли 14 нових інтеграційних
тестів і 20 підперевірок, включно з аварійним завершенням до/після commit.

Наскрізного автомата ще немає: адаптери не створюють усі потрібні receipt,
job aliases, закриті сегменти та перевірені докази фактичних витрат. Worker,
resolver і workflow звіряння залишаються наступними етапами. У Studio
автосписування продовжує позначатися як незавершене й не ввімкнене.

## Реалізована межа першого ядра

- Один `COMPLETED` job з відомими start/end і рівно одним material/segment.
- Сегмент закритий на весь інтервал друку; призначення й монтаж перевірені;
  слот/монтаж належать правильному принтеру.
- Доказ — `PRINTER / CONSUMED_MASS / ABSOLUTE`, confidence 10000,
  відоме `includes_purge=True`, точний інтервал і посилання на receipt/alias.
  Оцінка слайсера, довжина чи непевний purge не перетворюються на факт витрат.
- Receipt має бути стійко збереженим `PENDING` і належати тому самому запуску.
- Відомий узгоджений залишок; початковий облік існував до початку друку.
  Післяпринтове зважування блокує сліпий дебет до звіряння cutoff.
- Finalization + decision + evidence link + ledger/projection + settlement
  власного резерву + job/receipt states + audit комітяться разом.
- Нульова маса зберігає decision і звільняє резерв без нульового ledger debit.
- Повтор з тим самим ключем/доказом/актором повертає збережений record.
  Зміна ключа або фактичного запиту дає конфлікт без повторного списання.

Недостатній запас, чужі резерви, карантин і неоднозначне mapping відхиляються
без змін; receipt/evidence залишаються для подальшої звірки. Автоматичне
створення incident із фізичним від’ємним залишком, AMS/кілька сегментів,
failed/cancelled prints і вибір між джерелами ще не реалізовані цим ядром.
Нова міграція не потрібна: використана чинна frozen v1 schema.

## Послідовність

1. Worker отримує подію та записує receipt у стійку чергу. Ключ обмежений
   provider instance + printer + source epoch + event identity; зберігається hash.
   Конфлікт того самого ключа з іншим payload не приховується як звичайний повтор.
2. Job resolver знаходить запуск за перевіреним ID/aliases. Ім’я файла, 100%
   прогресу або час отримання повідомлення не є достатньою ідентичністю.
3. Прив’язуються матеріали й часові сегменти котушок/слотів. Одночасна зміна
   котушки та завершення завдання не повинні приписати витрати новій котушці.
4. Evidence нормалізується. Маса з принтера, довжина екструзії, оцінка слайсера
   й вимірювання вагами мають різні типи. Невідома щільність не підставляється
   довільно. Для довжини: об’єм циліндра за діаметром × щільність, із явними
   одиницями та правилом округлення до міліграма на межі.
5. Versioned policy формує immutable decision: вибране джерело, причина,
   confidence, сумарні й покотушкові витрати, включення purge/waste, межі похибки.
   Не сумувати snapshot-cumulative значення як окремі deltas.
6. Під однією транзакцією UoW: перевірити job/finalization, актуальні ревізії,
   наявність запасу/власних резервів; записати decision, усі ledger entries,
   settlement резервів, finalization та processed receipt; потім commit.
7. Повтор після рестарту повертає збережений результат. Не використовувати
   набір «уже бачених» у RAM як основний захист.
8. Неоднозначність створює reconciliation task. UI показує котушки, джерела,
   оцінку та причину. Підтвердження або компенсація — нова журналювана команда.

Викликати `deduct_manual()` для кожного AMS-слота окремими транзакціями не
можна: збій посередині залишить частково списане багатоматеріальне завдання.
Виконавець має використовувати один UoW і повний набір операцій.

## Перший конкретний етап коду

Перший application service `finalization.py` та потрібні порти реалізовано.
Наступне: стійка ingest-черга й resolver з гарантованою ідентичністю запуску;
реальні адаптери мають явно відрізняти фактичну витрату від оцінки.
Не змінювати frozen v1 migration.
Якщо потрібні нові обмеження схеми — окрема v2 міграція з pre-migration backup.

До підключення реального worker довести service інтеграційними тестами.
Далі: стійка ingest-черга → job resolver → mapping/evidence → policy → UI
звіряння → read-only shadow mode → реальний друк → контрольоване ввімкнення.
Shadow mode порівнює запропоноване списання з фактом, але не змінює залишок.

## Обов’язкові сценарії прийняття

- Одне завершення — одне списання; 100 повторів і повтор після рестарту — те саме.
- Два одночасні виконавці — один finalization, без подвійних ledger entries.
- Crash до commit — жодної часткової зміни; після commit — replay без другої зміни.
- Той самий G-code запущено двічі — два окремих job і два правильних списання.
- Reconnect/reset epoch/reordered events не породжують вигадане нове завдання.
- Unknown mass, відсутня котушка, застаріле mapping або непевна identity — звіряння.
- Успіх/скасування/брак розділені; фактично витрачений пластик не повертається
  автоматично лише тому, що друк скасовано.
- Purge, load/unload та failed print не враховані двічі з різних джерел.
- AMS rollover і заміна котушки зберігають правильні сегменти й котушкові витрати.
- Власний резерв settlement узгоджується з витратами; чужі резерви збережені.
- Недостатній/карантинний запас не призводить до прихованого від’ємного залишку.
- Компенсація зберігає первинну історію; audit не містить токенів або access code.

## Ввімкнення

Автосписування не активувати до проходження replay/crash/concurrency тестів,
перевірки фактичного принтера і явного вибору єдиного облікового власника.
Spoolman/HaspelSync і UFM не повинні незалежно коригувати один і той самий
спільний журнал за те саме завдання. Перша підтримувана конфігурація — один
локальний принтер і одна котушка; AMS та ферма — наступні контрольні етапи.
