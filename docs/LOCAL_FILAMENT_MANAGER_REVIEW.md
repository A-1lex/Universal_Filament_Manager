# Аналіз локального Filament Manager

Дата огляду: 24 жовтня 2026 року.

## Що знайдено

У `D:\Filament_Manager` розгорнута зв'язка двох окремих застосунків:

| Компонент | Встановлений образ | Призначення |
| --- | --- | --- |
| Spoolman | `filament-manager/spoolman:0.27.0-uk` | Каталог виробників, матеріалів і котушок, залишки, етикетки, API |
| HaspelSync | `filament-manager/haspelsync:1.3.4-uk` | Зв'язок із Bambu через LAN MQTT/FTPS, прив'язка котушок, облік друку |

Це окрема встановлена система. Вона не є зібраною версією Universal Filament Manager.
Docker підтвердив роботу обох контейнерів. Spoolman відповів HTTP 200 на
`http://127.0.0.1:7912/api/v1/info`; HaspelSync повернув сторінку входу HTTP 200
на `http://127.0.0.1:4000/`. Обидва опубліковані порти прив'язані до localhost.

Поточні дані, отримані через API Spoolman без змін:

- 5 активних котушок, 0 архівних;
- 5 записів філаменту, 2 виробники;
- 4 котушки мають ненульове значення використаної маси;
- сумарно записано 819,448 г використання і 4180,552 г залишку;
- у конфігурації HaspelSync є один принтер.

Це значення обліку, а не підтверджене фізичне зважування. Наявність витрат сама
по собі не встановлює, чи внесені вони автоматично або вручну. Поточне з'єднання
принтера і повний цикл реального друку під час огляду не перевірялися.

## Що вже реалізовано

Spoolman має Python/FastAPI/SQLAlchemy backend і вебінтерфейс. У локальній базі
9 таблиць разом із таблицею версії міграцій. Є облік котушок, виробників,
матеріалів, додаткових полів, тегів та налаштувань. Присутні автоматичні резервні
копії; найновіша побачена копія датована 23 жовтня 2026 року.

HaspelSync використовує Node.js/Express, MQTT для стану Bambu та FTPS для
отримання нарізаного файлу. За локальним кодом підтримує AMS і зовнішню котушку,
ручну прив'язку до Spoolman, читання 3MF/G-code, завершений і перерваний друк,
відновлення частини стану після перезапуску, дашборд і журнали. На завершенні
друку витрата береться з оцінки слайсера; для невдалого/скасованого друку
обчислюється часткова витрата з урахуванням завершених шарів та доступних даних
екструзії. Це розрахункова витрата.

Українська локалізація накладена локальними Docker-образами. Dockerfile HaspelSync
додає словник `uk.js`; Dockerfile Spoolman збирає локальний `client_v2` поверх
зафіксованого базового образу. Опис локалізації повідомляє про доповнення
482 повідомлень Spoolman і переклад 826 повідомлень HaspelSync. Повний мовний
тест під час цього огляду не запускався.

## Важливі відмінності обліку

1. **Неоднозначна котушка може отримати повну витрату.**
   `localization/haspelsync/src/mqtt.js:1462` містить гілку, яка за кількох
   нерозрізнюваних кандидатів повідомляє про неоднозначність і списує всю масу
   на `matches[0]`. Для UFM такий випадок має залишатися невирішеним до
   підтвердження користувачем.

2. **Багатоматеріальне списання не є однією транзакцією.**
   `mqtt.js:1435` перебирає матеріали і окремо викликає Spoolman. Одна котушка
   може бути успішно списана, а інша отримати помилку. Обробник помилки створює
   рядок результату `failed`, але не відкочує вже успішні запити.

3. **Не виявлено завершення друку з довговічною атомарною квитанцією.**
   `mqtt.js:907` встановлює прапорець у пам'яті `consumptionBooked` і видаляє
   збережений старт перед виконанням списань. `printstate.js` зберігає старт,
   шлях файлу та слоти активного друку, але не спільну зі Spoolman транзакцію
   завершення. Запит у `spoolman.js:615` надсилає масу без ключа ідемпотентності.
   Відновлення після збою в цей момент і повтор мережевого запиту потребують
   окремої перевірки. Збій під час огляду не відтворювався.

4. **Баланс змінюється без незмінного журналу операцій UFM.**
   `localization/spoolman/spoolman/database/spool.py:777` змінює `used_weight`
   атомарним SQL-приростом, що захищає від втрати паралельного приросту. Проте
   це не захист від повтору тієї самої події. `models.py:95` використовує
   `float`, а в оглянутій базі немає окремих таблиць журналу списань і
   фіналізації завдань, аналогічних запланованим в UFM.

5. **Інша модель зберігання доступу до принтера.**
   Локальний README HaspelSync прямо описує LAN-код у
   `printers/printers.json`. `src/gcode.js:22` повертає
   `rejectUnauthorized: false` для FTPS. Це відрізняється від запланованого
   OS SecretStore та перевірки довіри в UFM. Значення приватних параметрів
   у звіт не включалися.

Ці висновки походять з огляду локальних вихідних текстів. Вони не є доказом
того, що перелічені помилки вже відбулися у встановленій системі.

## Порівняння з Universal Filament Manager

| Можливість | Встановлена система | UFM зараз |
| --- | --- | --- |
| Інтерфейс для повсякденного використання | Є вебінтерфейси | GUI ще немає |
| Дані реальних котушок | Є 5 записів | Є команди обліку, імпорту ще немає |
| Bambu LAN, зовнішня котушка та AMS | Реалізовано в HaspelSync | Є контракти, адаптера немає |
| 3MF/G-code і автоматичне списання | Реалізовано | Ще не реалізовано |
| Незмінний журнал із точною масою | Інша модель, змінюваний `used_weight` | Реалізовані журнал і цілі міліграми |
| Резервування матеріалу | В оглянутих модулях відповідного механізму не виявлено | Є основні команди й перевірки місткості |
| Атомарна фіналізація всього друку | В оглянутому шляху списання немає | Запланована, ще не реалізована |
| Спосіб запуску | Docker і браузер | Python CLI, запланований desktop |

Встановлена система значно попереду за доступними користувачеві функціями.
UFM уже має частину суворіших облікових примітивів, але повний безпечний цикл
друку ще потрібно реалізувати і перевірити.

## Як використати результат огляду

Для розвитку UFM корисні сценарії екранів Spoolman, ручна прив'язка зовнішньої
котушки HaspelSync, нормалізація MQTT, пошук файлу через FTPS, розрізнення
повторного друку й відновлення, а також реальні тестові приклади 3MF.
Найближчий обмежений сценарій для UFM: імпорт котушок з явним підтвердженням
початкової маси, завершення облікового ядра, потім P1S із зовнішньою котушкою.
Імпорт має зберігати відповідність Spoolman ID і UFM UUID та позначати залишки
як прийняті розрахункові дані. Двом системам не слід одночасно списувати одну
фізичну витрату в один облік.

У локальних файлах вказані MIT для Spoolman та GPL-3.0-only для HaspelSync.
Код цих застосунків у UFM під час огляду не переносився.

Початковий `D:\Filament_Manager\README_uk.txt` застарів: він ще описує стан
до запуску контейнерів, тоді як їхню поточну роботу підтверджено Docker та HTTP.

## Межі огляду

Прочитані конфігурація розгортання, локальні джерела, метадані залежностей,
схема SQLite та API обліку. Не змінювалися залишки, налаштування, дані принтера
або стан контейнерів. Не виконувалися оновлення, перезапуски, імпорт чи
апаратні тести. Тести сторонніх проєктів не запускалися. Створено лише цей
звіт у робочому каталозі UFM.
