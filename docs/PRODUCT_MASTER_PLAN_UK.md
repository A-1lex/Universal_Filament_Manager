# UFM Studio: повний пакет реалізації

Деталізація цього плану зі збереженням наявних кнопок і сценаріїв:
[INTEGRATION_STEP_BY_STEP_UK.md](INTEGRATION_STEP_BY_STEP_UK.md) — 17 частин,
118 кроків із результатами й критеріями готовності. Відмітки виконання:
[INTEGRATION_CHECKLIST_UK.csv](INTEGRATION_CHECKLIST_UK.csv).

## Результат і межі

Один нативний застосунок Windows для філаменту, принтерів і обліку друку.
Без браузера, Docker та обов’язкового зовнішнього Spoolman. Приватна локальна
база з резервними копіями; підключення до інших систем — додаткові адаптери.
Інтерфейс організовано за робочими просторами на зразок Bambu Studio, із власними
ресурсами й піктограмою. Повний слайсер не є умовою першого випуску:
спершу інтеграція зі слайсерами та перевірка файлів друку.

Цей пакет є планом повного продукту та першою працездатною реалізацією Studio.
Усі пункти зі станом «Додати» ще не реалізовані. План не є звітом про їх готовність.

## Що вже працює

- Python/SQLite ядро з міграціями, точними міліграмами, append-only журналом,
  ідемпотентними ручними командами й перевіреними snapshot-копіями.
- Qt Studio: котушки, пошук, метрики, історія, створення профілю та котушки,
  початковий залишок, ручне додавання/списування, світла й темна тема.
- Імпорт Spoolman через попередній перегляд і резервування джерела;
  повторне застосування до того самого джерела захищене ключами імпорту.
- Локальні read-only адаптери Bambu LAN, Moonraker, OctoPrint; обмежений
  LAN discovery. Налаштування принтера перевіряється перед збереженням.
- Майстер Qt для локальних HTTP-адаптерів і профілю Bambu Studio з перевіркою
  сертифіката. Секрети — у сховищі ОС, не в таблиці чи текстовому конфігу.
- Довідковий каталог матеріалів та SVG QR-етикетки існують у ядрі/CLI;
  їх повне графічне керування ще потрібно перенести в Studio.
- Є перша автономна onedir Windows-збірка з Python і Qt всередині та оригінальна
  іконка. Локальний EXE smoke пройшов; чиста Windows ще не перевірена.

`linked-stack/haspelsync` — збережена локальна розробка й джерело вимог,
а не видалений «зайвий» каталог. Її booking/accounting/weighing сценарії
потрібно переносити через перевірені контракти й тести. Стару Docker-систему
не вимкнено; копія даних Studio є незалежною, постійної синхронізації немає.

## Що обов’язково додати до основного випуску

Надійний worker, ідентичність запуску друку, зіставлення котушок і слотів,
evidence/decision/finalization workflow, автоматичне списування з відновленням
після збою, зручне виправлення неоднозначностей; керування життєвим циклом
котушки, цінами й місцями; стабільні підключення принтерів; керовані команди
лише за підтвердженими capabilities; відновлення копій; інсталятор та підпис.

Бажані наступні можливості: USB/NFC/RFID/ваги, сушарки й датчики вологості,
розширена камера й timelapse, ферма принтерів, глибока аналітика, віддалений
доступ за окремою моделлю довіри, SDK сторонніх адаптерів, 3D/G-code перегляд.

Точна деталізація станів: [FEATURE_MATRIX_UK.csv](FEATURE_MATRIX_UK.csv).

## Перші контрольні релізи

**Preview A — локальний склад:** W01–W05, базові W06–W08 і W30. Поточна
ітерація дала частину цього результату; графічне редагування, повні атрибути
профілів, зважування та lifecycle ще не завершені.

**Preview B — облік друку:** W09–W15. Спершу один принтер і одна котушка
без AMS, потім багатоматеріальний шлях. Жодного сліпого автомата за «100%».
Сценарій прийняття: початок → прив’язка → завершення → списання → повтор
події → перезапуск програми → повторна доставка; залишок змінюється один раз.

**Beta — управління обладнанням:** W16–W21, W27–W28. Увімкнення фізичних
команд тільки для перевірених моделей/прошивок та конкретних capabilities.
Автовиявлення моделі не означає дозвіл довільних G-code/macros.

**Release 1.0:** W30–W32, усі обов’язкові функції матриці й тести реального
сценарію. Бажані можливості W22–W26 можна поставляти пізніше, якщо основний
сценарій не залежить від них. Ферма та хмарний доступ не повинні затримувати
надійний локальний облік одного принтера.

## Архітектурні рішення

Зберегти перевірене Python-ядро. Qt Widgets дає нативне оформлення й працює
без WebView. Нові UI-контракти відокремлювати від persistence; нинішній
StudioBackend — тонка інфраструктурна read-model/command facade, яку далі
треба винести за application port. SQL-обхід журналу для зміни маси заборонений.

C++/Rust додавати для виміряних задач 3D та великих парсерів. C#/.NET —
альтернативний Windows frontend за окремим рішенням; не вести дві оболонки
паралельно без потреби. Адаптери працюють через DTO/capabilities, не пишуть SQL.

Для дизайну й сценаріїв використані офіційні описи
[Bambu Studio](https://github.com/bambulab/BambuStudio),
[OrcaSlicer](https://github.com/OrcaSlicer/OrcaSlicer),
[Mainsail](https://docs.mainsail.xyz/),
[OctoPrint](https://docs.octoprint.org/en/master/features/index.html).
Це джерела вимог та організації UI; їх код не копіюється автоматично.

## Правила прийняття й перевірки

Для кожної операції обліку: точні величини; unknown/stale; повтор; конкурентний
виклик; crash до/після commit; негативний сценарій без часткового запису.
Для адаптера: fixture server, обмеження payload/timeout, offline/auth/TLS,
перезапуск/прошивка, capabilities, фізична перевірка перед активацією команд.
Для релізу: відсутність Python/Docker на чистій машині, Unicode-шляхи,
звичайний користувач без admin, sleep/resume, backup/restore/update/uninstall.

Не видаляти старі джерела до завершення порівняння і перенесення локальних
правок. Зараз очищення дозволене лише для відтворюваних кешів. Мережеве
підключення чи підтримка конкретної прошивки не вважаються перевіреними
лише через успішне збирання EXE.
