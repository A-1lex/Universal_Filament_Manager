Перевірено 26 жовтня 2026 року: офіційні документація/вихідні файли проєктів,
локальний Spoolman 0.27.0, завантажений HaspelSync 1.3.4, власний checkout

Це порівняння; код застосунку й дані принтера під час огляду не змінювалися.

## Основний висновок

Spoolman зберігає котушки та приймає зміни через API. Визначення витрат,
активної котушки й моменту списування виконує підключена система.
Це прямо описано в [офіційній документації Spoolman](https://github.com/Donkie/Spoolman/wiki/Automatic-Filament-Usage-Tracking).

Тому робоче автосписування не потребує обов’язкового датчика фізичної маси.
Можна використовувати команди екструзії або розрахунок слайсера; джерело,
похибку й спосіб отримання потрібно зберігати та показувати окремо.

## Як працювала ваша зв’язка

```mermaid
flowchart LR
    P[Принтер Bambu] -->|MQTT: стан і слоти| H[HaspelSync]
    P -->|FTPS: gcode.3mf| F[Парсер файла]
    F -->|Маса та розподіл матеріалів| H
    H -->|Завершення або розрахована частина| U[Spoolman API /spool/id/use]
    U -->|Приріст used_weight| D[База залишків]
```

Локальні вихідні файли підтверджують таку послідовність:

1. `localization/haspelsync/src/mqtt.js:611` стежить за станом друку. На старті
   зберігаються ідентичність запуску, файл і котушки/слоти.
2. `.gcode.3mf` отримується через FTPS. Парсер використовує `used_g` та
   відомості про логічні матеріали/шари; MQTT mapping допомагає прив’язати їх
   до реальних слотів. Без AMS зовнішній тримач теж є слотом.
3. При `FINISH` використовується повний розрахунок
   (`gcode.js:1031`, `mqtt.js:944`). При невдалому/скасованому друці — частковий
   (`gcode.js:1319`): доступні частки екструзії за шарами; інакше діапазони шарів
   матеріалу; ще один fallback — частка завершених шарів. Це оцінка, не ваги.
4. `mqtt.js:1377` зіставляє витрати з котушками. Неприв’язаний матеріал
   пропускається з повідомленням. У завантаженій версії неоднозначність кількох
   котушок може віднести всю витрату на першу (`mqtt.js:1462`).
5. `spoolman.js:615` надсилає приріст маси через `PUT /api/v1/spool/{id}/use`
   з `use_weight`. Матеріали записуються окремими запитами, а не спільною
   транзакцією всього друку.
6. Локальний `spoolman/database/spool.py:777` атомарно додає масу до
   `used_weight`; залишок обчислюється із початкової маси та використання.
   Для `use_length` (`:826`) довжина переводиться в масу за діаметром і щільністю.
   Той самий запит `/use` повторно збільшує використання: сам endpoint не
   ідентифікує унікальне завершення друку.

Є також legacy RFID-режим, що орієнтується на повідомлений AMS відсоток залишку.
Його не слід одночасно застосовувати як незалежне друге списування за G-code.
Режим automatic/manual у HaspelSync стосується насамперед створення/зіставлення
котушок; ручне зіставлення не означає ручне списування кожного друку.

## Підтвердження з ваших журналів

Знайдено узгоджену пару записів за часом журналів:

- HaspelSync: `2026-10-24_22:47:17`, повідомлення про **180.88 г для spool 3**;
- `D:/Filament_Manager/spoolman/spoolman.log:3069`: того самого часу
  `PUT /api/v1/spool/3/use` із HTTP **200**.

У збережених Spoolman-файлах журналів знайдено загалом **10 запитів `/use`**,
усі з HTTP 200. Це кількість запитів у наявних журналах, не кількість унікальних
друків. Вони підтверджують роботу зв’язки та прийняття списань; фізичну точність
розрахованої маси журнали не доводять. Приватні конфігурації/секрети не включено.

## Власна розробка вже має корисний захист

У `linked-stack/haspelsync/src/bookings.js:63` є стійкий booking journal:
ключ за принтером, початком запуску й матеріалом; hash запиту; стан до HTTP-запису;
повтор успіху повертає попередній результат. `spoolman.js:660` вимикає автоматичний
повтор `/use`; невизначена відповідь лишає `pending/uncertain` для звіряння.

Це покращення порівняно із завантаженою локальною версією. Воно не створює
спільної транзакції JSON-журналу та віддаленої БД Spoolman, але запобігає сліпому
повтору. Знайдені тести `test/bookings.test.js` перевіряють такі сценарії;
під час цього огляду їх повторно не запускали. Доробку потрібно зберегти.

## Порівняння інших реалізацій

| Реалізація | Основа витрати | Момент запису | Що варто використати |
|---|---|---|---|
| HaspelSync + Spoolman | Дані слайсера/3MF та часткова екструзія | На кінцевому стані друку | Bambu MQTT/FTPS; mapping; зовнішня котушка; частковий друк |
| Moonraker + Spoolman | Прирости координати екструдера | Пакетами під час роботи | Ретракція не списується повторно; прив’язка активної котушки |
| OctoPrint-Spoolman | Інтерпретація відправлених G-code за інструментами | На паузі та завершенні/збої/скасуванні | Попередня перевірка котушки; tool mapping; часткові витрати |
| Spoolman Updater + Home Assistant | У прикладі P1S/X1C: маса завдання × прогрес | Автоматизації/зміни активного слота | Простий сумісний fallback із позначкою низької впевненості |
| Поточний UFM | Лише перевірений повний факт маси | Одна локальна транзакція | Replay/crash/concurrency та точний журнал; джерела оцінок ще підключити |

Moonraker у [вихідному spoolman.py](https://raw.githubusercontent.com/Arksine/moonraker/master/moonraker/components/spoolman.py)
рахує приріст вище попереднього максимуму E, накопичує довжину для активної
котушки й надсилає `use_length`. За помилкою повертає пакет у pending RAM.
Активний spool ID записується в БД; pending-словник у цьому файлі є пам’яттю
процесу. Повторні HTTP-запити й рестарт залишають окремі облікові ризики.

[OctoPrint-Spoolman PrinterHandler](https://raw.githubusercontent.com/mdziekon/octoprint-spoolman/master/octoprint_Spoolman/modules/PrinterHandler.py)
обробляє вже відправлені G-code, збирає довжину за інструментом і передає її
через [SpoolmanConnector](https://raw.githubusercontent.com/mdziekon/octoprint-spoolman/master/octoprint_Spoolman/modules/SpoolmanConnector.py).
Це відстеження команд, а не фізичний датчик: прослизання механізму саме по собі
не вимірюється. Є окремий захист від парного cancel/failed event.

Приклад [Spoolman Updater](https://github.com/marcokreeft87/spoolman-updater)
використовує Home Assistant та оцінку маси через прогрес. Розподіл витрат
нерівномірний між шарами/кольорами, тому його не варто приймати за точний
покотушковий факт. Репозиторій на час огляду позначений archived.

Поточна [документація HaspelSync](https://raw.githubusercontent.com/Rdiger-36/HaspelSync/main/docs/how-it-works.md)
також описує списання за sliced-файлом на кінцевому стані та потребу slot link.
Маркетингове формулювання про точність не замінює фізичної калібровки;
дві цифри після коми у записі не означають таку ж фізичну точність.

## Наслідок для UFM

Нинішній `finalization.py:219` дозволяє лише PRINTER/ABSOLUTE, confidence 10000
і явний purge. Це навмисно вузький перший тестовий виконавець; звичайна оцінка
Bambu/3MF не пройде цей guard. Самого ядра недостатньо для паритету з HaspelSync.

Для наступної реалізації потрібні окремі політики:

1. **Bambu/3MF:** перевірений sliced-файл → грами матеріалів → slot/spool mapping
   → кінцеве списання з джерелом `THREE_MF/GCODE/SLICER` і позначкою оцінки.
2. **Частковий друк:** екструзія за завершеними шарами, потім layer-range fallback;
   глобальний progress — останній варіант із нижчою впевненістю.
3. **Klipper/OctoPrint:** стійко збережені прирости довжини; захист ретракцій і
   reset counters; перерахунок у масу з явними параметрами профілю.
4. **Зважування:** окреме inventory evidence і reconciliation, а не друге
   незалежне списання тієї самої витрати.

Усі ці режими можуть працювати автоматично за обраною політикою. Інтерфейс має
показувати джерело та якість оцінки. Спільний UFM ledger зберігає ідемпотентність
і атомарність; для multi-spool потрібне розширення single-segment service.
Не слід просто зняти наявні guards без визначення coverage, purge і повторів.

Рекомендований наступний зріз для вашого Bambu: перенести перевірений шлях
MQTT → FTPS/3MF → прив’язка зовнішньої котушки → оцінкове списання на FINISH,
спершу в shadow mode. Далі — часткові друки й AMS. Облікові записи та історію
показувати в одному Qt-інтерфейсі; Spoolman-сервер для цього не обов’язковий.

## Додаткова звірка власного HaspelSync/UFM — 29 жовтня 2026

Повторно перевірено локальний `linked-stack/haspelsync` і поточні джерела UFM.
HaspelSync визначає `freshStart` як перехід із неактивного стану в активний
(`src/mqtt.js:622`), фіксує час початку та намагається відновити його після
перезапуску за парою printer + job name (`src/mqtt.js:757`, `src/printstate.js`).
На термінальному переході лише один раз за активний стан готується повна чи
часткова оцінка. Для кожного sliced item та котушки `bookings.js` формує
ідемпотентний ключ із printer ID, `startedAt` та `itemKey`, записує намір до
HTTP-запиту; конфлікт параметрів блокує повтор, а невизначена відповідь
залишається на ручне звіряння. Це захист рівня інтеграції, бо Spoolman `/use`
сам не дедуплікує запит.

Цей шаблон корисний для політики обліку й recovery, але job name/локально
запам’ятаний час не є універсальним підтвердженим ключем принтерного запуску.
У Bambu Studio `BBLSubTask::task_id` описаний як plate ID, а `task_name` — як
зазвичай ім’я файла (`D:/GIT/BambuStudio/src/libslic3r/ProjectTask.hpp`);
ці поля не доводять семантику ID, що приходить у кожному LAN MQTT-звіті.
Поточний UFM LAN adapter лишає `provider_run_key` порожнім і створює новий
`source_epoch` для підключення. Отже, не копіювати HaspelSync key буквально:
для UFM потрібен або підтверджений provider run ID, або власний durable start
record, який переживає reconnect/restart і переводить неоднозначність у review.

### Рішення для наступного технічного кроку

- Зберегти з HaspelSync підхід «намітити до незворотного запису» та стан
  `pending/uncertain` без автоматичного повтору після невідомої відповіді.
- Не використовувати файл/job name як єдину ідентичність і не вважати
  `task_id` exact run, доки це не підтверджено MQTT trace/fixture для локального
  друку та повторного друку того самого файла.
- Перед consumer-ом узгодити exact run key, provider payload digest/provenance,
  повторні події після reconnect та атомарний спільний writer для UFM/HaspelSync.
  Поточний `ReceiptIngestion`/`ProjectionDrain` runtime не активований; списання
  залишається вимкненим.
