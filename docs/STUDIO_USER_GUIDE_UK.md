# UFM Studio: запуск і робота

## Де програма

- Програма: `D:\UFM Studio\UFM Studio.exe`.
- Дані цього комп’ютера: `D:\UFM Studio Data`.
- Вихідний код: `D:\Bot\Universal_Filament_Manager`.
- Папку `_internal` потрібно залишити поруч із EXE. На цьому комп’ютері
  перевірено запуск із вбудованими Python та Qt; браузер і Docker не потрібні.
- Звичайний запуск EXE без аргументів використовує стандартні користувацькі
  каталоги Windows. Ярлик цього комп’ютера використовує `--data-dir` з папкою вище.

Початкова копія містить 5 котушок, 5 профілів та 2 виробників із локальної
бази Spoolman. Це окремий облік: наступні зміни у Spoolman чи HaspelSync
не синхронізуються зі Studio автоматично. Історичні операції друку не імпортовані.
Перед використанням Studio як основного обліку вимкніть списування для тих самих
завдань у старій системі, щоб не вести дві незалежні версії залишків.


## Внутрішня тестова збірка

Найновіша portable-збірка для перевірки коду — Candidate16: `D:\UFM_TestCandidate16\UFM Studio\UFM Studio.exe`. Її маніфест перевірений (378 файлів), але Candidate16 ще не запускали й не оглядали в UI. Щоб запустити ізольовано через PowerShell, виконайте:

```powershell
& 'D:\UFM_TestCandidate16\UFM Studio\UFM Studio.exe' --data-dir 'D:\UFM_TestCandidate16\Data' --locale uk-UA
```

Це створить/використає окремий каталог даних Candidate16; не передавайте шлях до встановленої програми. Ярлик Candidate16 не створювали.

Останній фактично оглянутий через UI кандидат — Candidate15, ярлик **UFM Studio — ТЕСТ Candidate15**. Він використовує `D:\UFM_TestCandidate15\Data`; його перевіряли на цій машині, але це не приймання власником, clean-Windows чи апаратна перевірка. Candidate16 та Candidate15 — внутрішні непідписані збірки `0.1.0.dev0`, не інсталятори й не публічний реліз; Candidate16 SBOM має `composition=incomplete`.

Під час ручного огляду перевірте вкладки, масштаб/читабельність і форми. Не переводьте обліковий режим у `UFM_ACTIVE`, не виконуйте cutover/rollback і не запускайте списання: віддалена взаємна блокіровка різних екземплярів Haspel ще не доведена. Для першого огляду не вводьте LAN-коди, API-ключі чи паролі.

## Початок роботи

1. Відкрийте ярлик **UFM Studio** або EXE.
2. На вкладці **Філамент** виберіть котушку. Праворуч видно профіль та історію.
3. Для нової котушки спочатку створіть профіль у **Матеріали**, потім натисніть
   **+ Котушка**. Нова котушка має невідомий залишок до введення початкової маси.
4. Маса вводиться у грамах, до трьох десяткових знаків; приймаються крапка та кома.
   Ручне списування не дозволяє перевищити доступний запас.
5. Пошук працює за назвою котушки, профілем і матеріалом. Кнопка у верхній частині
   перемикає світле й темне оформлення.
6. У **Система** доступні резервна копія та імпорт SQLite-бази Spoolman.
   Імпорт спочатку показує кількість записів і потребує підтвердження у програмі.
   Резервні копії джерела зберігаються в каталозі даних; оригінал не редагується.

## Пристрої

Пошук перевіряє обмежену приватну IPv4-підмережу та порти підтримуваних
адаптерів. Відкритий порт означає кандидата, а не доведену модель принтера.
Пошук і читання стану запускаються кнопкою й не блокують інтерфейс.

Studio показує налаштовані в UFM принтери. **Майстер підключення принтерів**
приймає параметри локального Moonraker/OctoPrint і перевіряє з’єднання перед
збереженням. Для Bambu кнопка **Bambu: знайти профіль Studio** знаходить
локальний профіль за IP, показує серійний номер та відбиток сертифіката;
після підтвердження довіри перевіряє підключення і зберігає секрет у Windows.
Цей спосіб потребує раніше налаштованого профілю LAN у Bambu Studio.

Кнопка **Автозаповнити з мережі** відкриває Bambu-форму з окремою кнопкою
визначення пристрою. Залиште IP порожнім, якщо у локальній мережі один принтер,
або введіть його адресу. SSDP дає назву/модель/IP/serial; serial звіряється з
TLS-сертифікатом. Якщо multicast недоступний або порт зайнятий Bambu Studio,
використайте IP: для P1S модель також визначається з документованого serial prefix.
Після підтвердження відбитка заповнюються поля; LAN-код введіть з екрана принтера.
Натисніть **Перевірити та зберегти**. Секрет зберігається тільки після успішного
підключення. Якщо знайдено кілька пристроїв, адреса має бути вказана явно.
У класичній формі додано таку саму кнопку поруч з імпортом Bambu Studio.
Не копіюйте access code, токени чи секретні JSON у папку розповсюдження.

Фізичні команди нагріву, руху, паузи й запуску друку та автоматичне списування
ще не реалізовані у Studio. Програма показує цей стан прямо в інтерфейсі.
Показ температури сам по собі не означає підтримку команд керування.

## Резервні копії та оновлення

Перед оновленням створіть резервну копію у вкладці **Система** і закрийте програму.
Пакет програми й особисті дані розділені: не додавайте `UFM Studio Data`
до архіву для інших користувачів. Не видаляйте `_internal` окремо від EXE.

Відновлення копії поки виконується засобами ядра UFM у новий шлях;
графічний майстер відновлення заплановано. Копія SQLite не включає секрети
Windows Credential Manager: на іншому ПК принтери потрібно авторизувати знову.

Автоматичної перевірки чи встановлення оновлень поки немає. Поточні unsigned
candidate не встановлюйте поверх робочої програми: перевірка підпису й
приймання оновлення ще не пройшли. Після окремого схвалення підписаного релізу
застосовуйте лише вручну підготовлений пакет, попередньо звіривши версію,
Authenticode, SHA-256 маніфесту та відповідний SBOM. Не робіть downgrade через
інсталятор; для повернення на старішу версію спершу потрібен перевірений
backup/restore та сумісна міграція БД. Протокол і критерії зібрано в
`docs/RELEASE_ACCEPTANCE_UK.md`.

## Готовність до розповсюдження

Це попередня автономна Windows-збірка. Залишаються перевірка на чистій Windows,
підпис EXE/інсталятора, вибір ліцензії власного коду, повний пакет сторонніх
ліцензій, перевірка оновлення/відновлення та реалізація функцій у матриці.
Наявність EXE не означає завершений паритет зі Spoolman, HaspelSync або слайсером.
Перед окремим acceptance користуйтеся [протоколом приймання Windows candidate](RELEASE_ACCEPTANCE_UK.md).

Для розробника: виконати `uv sync --extra desktop --extra dev`, запускати
`python -m ufm.ui.studio`. Відтворюваний folder candidate:
`scripts/build_release_candidate.ps1 -DestinationParent 'D:\UFM_ReleaseCandidate'`.
Він створює окреме `.venv-release` з `uv.lock` (Python 3.12.15, desktop і
зафіксований PyInstaller) і не змінює робоче `.venv312`. Зібрана папка не є
інсталятором і ще не прийнята runtime-перевіркою. Не замінюйте встановлену
`D:\UFM Studio` і її ярлик до окремого погодженого приймання. Звичайний
`scripts/build_studio.ps1` лишається низькорівневим кроком; він також вимагає
новий каталог призначення, якщо ціль уже існує.

Історичний installer Candidate4 був непідписаний і не пройшов установку,
видалення чи оновлення; не використовуйте його як актуальну інструкцію або
публічний пакет. Поточний `build_installer.ps1` навмисно відмовляється від
компіляції, доки не надано повний CycloneDX SBOM із затвердженим license review,
stable версію X.Y.Z і manifest чистого Git source revision із відповідними
input hashes, а bundle EXE та installer не підписані одним затвердженим Code
Signing сертифікатом із timestamp. Нинішній генератор SBOM помічає inventory як
неповний, тому релізний installer ще не можна зібрати; portable Candidate15
залишається лише внутрішньою тестовою збіркою. Публічний реліз наразі не готовий.
`build_release_candidate.ps1` створює SBOM поруч із кожною новою папкою
candidate й відмовляється перезаписувати наявну папку або SBOM.
`build_installer.ps1` перед компіляцією вимагає sidecar для цієї папки та
звіряє версію, SHA-256 build manifest, SHA-256 runtime inventory, повноту
інвентаризації, license-review approval і підписи. Для вже зібраної папки
поточний генератор може сформувати лише неповний SBOM:
`python scripts/write_release_sbom.py 'D:\UFM_ReleaseCandidate4\UFM Studio' 'D:\UFM_ReleaseCandidate4\UFM Studio.cdx.json' --node-version 24.22.1 --qt-version 6.12.0`.
Версії передаються зі статичних PE `ProductVersion` bundled `node.exe` та
однакових Qt DLL; жоден runtime не запускається. Документ перевіряється
офіційною JSON Schema CycloneDX 1.7 та явно позначається неповним. Він містить
Python-залежності з `uv.lock`, окремі Node.js/Qt компоненти й лише мінімальний
vendored набір HaspelSync розрахунків, прив’язані до файлів перевіреного
manifest. Повний граф інших native компонентів, ліцензійна оцінка та юридичне
схвалення лишаються відкритими.

### Остання збірка для ручної перевірки UI

Останній UI-перевірений build — Candidate15: ярлик на робочому столі
`UFM Studio — ТЕСТ Candidate15.lnk`. На вкладці **Пристрої** є дія
**Перевірити локальний 3MF/G-code**. Вона лише читає обраний локальний файл:
для 3MF показує валідовані доступні пластини, SHA-256 і розрахункові грами за
логічними каналами; для G-code — підтримувані інструменти/шари та довжину
екструзії у міліметрах. Файл не прив’язується до завдання, не виконується і не
списує філамент. Невідомий G-code dialect може бути відхилений; грамів із
standalone G-code не обчислюємо. Використовуйте тільки файли, якими можете
ділитися локально; цей перегляд не надсилає файл на принтер чи сервер.

Candidate15 — внутрішня непідписана тестова збірка з окремими даними
`D:\UFM_TestCandidate15\Data`; вона не замінює встановлену програму чи дані.
Перевірте вручну вкладки, форми, масштаб, навігацію клавішею Tab, підказку для порожнього каталогу матеріалів і кнопку
локального огляду на безпечній копії файла. Не вводьте LAN-код і не вмикайте
облік у цій UI-перевірці. Ярлики Candidate5/7/8/9/10/12/13/14 відкривають попередні
тестові версії. Старі `UFM Studio.lnk` та `Universal Filament Manager.lnk`
ведуть відповідно на встановлену й development версії; для останнього UI тесту
обирайте Candidate15 для повторення вже перевіреного UI або Candidate16 для
перевірки найновішого коду. Candidate16 ще потребує першого запуску та огляду;
для нього використовуйте окремий каталог даних, описаний вище.
